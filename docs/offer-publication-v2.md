# 案件金額の公開ルール v2（2026-11-24 運営者決定）

2026-11-24 のシステム調査で、公開中の金額の多くが 9/28 のまま更新されていないこと、19 ゲーム中 18 ゲームに「掲載情報を確認中」が出ていること、GitHub の定期実行が抜けた日にデータが更新されないことが分かった。運営者が決めた方針と、その実装場所をまとめる。

## 運営者の決定

| 項目 | 決定 | 実装 |
| --- | --- | --- |
| 1 サイトだけで確認できた金額 | 確認日つきで「掲載確認済み」と表示する（2 サイト未満であることは警告にしない） | `site-data.js` `getOfferHealthLabel` |
| モッピーの StepUp（公開ページは合計額のみ） | 合計額を毎日更新し、「各成果地点の条件はモッピーで確認」と条件欄に注記する | `scripts/structured_publication.py` `moppy_stepup_total_only` / `MOPPY_TOTAL_ONLY_NOTE` |
| 毎日の確認で取り直せなかった古い金額 | 確認（`updatedAt`）から 7 日を超えたら表示しない。CSV の行は消さない | `site-data.js` `isOfferFresh`、`config/refresh_policy.json` `publication.maxOfferAgeDays` |
| 作り直す範囲 | 金額の取得と公開（攻略記事の自動生成は対象外） | — |

## 変えていないこと

- 各サイトのページ解析（`direct_offer_refresh.py` の `inspect_*`）。
- モッピー以外の公開条件（OS・期限・単位・指紋・提供元・StepUp 全段階の一致）。
- 公開データの列構造、行の削除ルール（ワラウ・ハピタスの 3 回連続終了のみ）。
- 7 日を超えた行は表示しないだけで、`data/published_offers.csv` には残る。7 日を超えて隠れたゲームは、`games.csv` の参考値（未確認）に置き換えない（`games.js`）。

## 運用の補強

- **予備の起動**：`.github/workflows/refresh-backup-trigger.yml` が 10:13 / 11:43 JST に `scripts/refresh_schedule_guard.py` で判定し、その日の更新が一度も作られていない場合だけ、通常の更新ワークフローを 1 回起動する。失敗・実行中・待機中の更新がある日は何もしない。このワークフロー自体はデータを書かない。GITHUB_TOKEN で起動した更新は workflow_run を発火しないため（2026-11-24 に確認）、起動した更新が成功するのを待ってから Pages デプロイを workflow_dispatch で起動する。有料APIを使う調査ワークフローは、予備起動の日は動かさない。
- **2026-11-24 の実測**：16:17 UTC の定期実行は消えたのではなく、約10時間40分遅れて 02:56 UTC に作られた。予備起動で先に更新した後なので、この日は更新が2回走った（データは上書きされるだけで害はない）。
- **保留理由の見える化**：日次更新のログに `PUBLICATION_HOLDS {...}` としてサイト別の公開数・保留数・保留理由を出す（URL・金額は出さない）。ハピタスやモッピー単一条件が保留される理由は、この行で確認する。

## 2026-11-24 に見つけて直したこと

- モッピーは同じ案件を `?site_id=N` と `?s_id=N&track_ref=category` の2つのURLで出す。同一判定キーが別々だったため、キングショットiOSが2行になった。キーを `moppy:site_id:N` に統一し、重複した1行を削除した。

## 次に見ること（未対応）

- ハピタス・モッピー単一条件の保留理由（次回のログの `PUBLICATION_HOLDS` で確認）。
- アメフリ・ミコシ・ゲンダマ・ポイントタウンは日次更新で解析成功 0 件が続いている。
- ニフティ（11/18〜）・クラシル（11/21〜）の一覧取得失敗と、それにより新作上位 5 件の引き継ぎが空になる仕組み（調査 API を使うワークフローにつながるため、別途判断）。
- 終了済みの旧案件 ID（約 90 件）を毎日取り直している。
